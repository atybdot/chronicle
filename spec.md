# Chronicle Multi-Agent Rewrite — Specification

## Problem Statement

Chronicle's current single-shot AI architecture has four fundamental problems:

1. **Rate limits exhausted instantly** — Every `chronicle backfill` run calls the LLM 2-3 times with aggressive retries. On free-tier providers like Groq, a moderate diff triggers 10+ API calls and hits rate limits in under a minute.

2. **Unnatural commit history** — Timestamps are generated by `distribution.ts` with `Math.random()` — weekday weights, session clustering, and offsets are all random with no relationship to real work patterns. The GitHub contribution graph doesn't look like real feature development.

3. **Wrong context** — Hunks are sent to the LLM with truncated previews and no file-level context. Multi-pass analysis degrades further with each pass. Fallback mechanisms dump unassigned hunks into per-file deterministic commits, producing incoherent groups.

4. **Hunk double-staging** — `unstageAll()` per commit masks but does not solve the problem of hunks being assigned to multiple commit groups. There is no exactly-once enforcement for hunk staging.

The solution is a full rewrite from scratch using a **multi-agent AI architecture** (Vercel AI SDK) where a supervisor agent dispatches work to specialized worker agents, with an auditor agent that reviews and signals problems for targeted re-generation — like backpropagation but with prompts.

Providers and models are abstracted via the AI SDK and added later with minimal code changes. The agent architecture itself is the core value.

## Solution

A CLI tool (Bun, monorepo) with 7 AI agents. The Orchestrator reads the user's free-form intent from config, delegates to 5 worker agents (FileAnalyzer, CommitPlanner, MessageWriter, TimestampDistributor, Executor), collects results into a plan, passes it to an Auditor for review, loops back on flagged commit groups until clean, then presents the plan for user approval before execution.

A Hunk Ledger (JSON state file) tracks every hunk's status to guarantee exactly-once staging. A hierarchical summarization strategy for context management handles large diffs gracefully.

## User Stories

1. As a CLI user, I want to run `chronicle backfill` and have it analyze uncommitted changes, so that commit groups are formed without any manual file selection.

2. As a CLI user, I want the tool to detect whether I'm in a git repo, so that it fails gracefully with a clear message if I'm not.

3. As a CLI user, I want the agent to read my free-form intent instruction from config (e.g., "Make it look like I worked feature-by-feature over 2 weeks"), so that the commit plan matches my personal style preferences.

4. As a CLI user with no configured intent, I want a sensible default (natural work pattern: weekdays, work hours, feature-coherent clustering), so that I get a good result without any setup.

5. As a CLI user, I want to see a visual plan summary after analysis (commits, categories, date range, per-day breakdown), so that I can understand what the agent decided before approving.

6. As a CLI user, I want to review the full commit plan before any commits are made, so that I can catch issues before they affect my git history.

7. As a CLI user, I want to approve, modify, or cancel the plan after review, so that I stay in control of my git history at all times.

8. As a CLI user, I want the ability to configure a dry-run mode, so that I can preview plans without ever making commits.

9. As a CLI user, I want each generated commit to contain only related hunks (atomic commits), so that the history is clean and each commit tells a single coherent story.

10. As a CLI user, I want commits from the same feature group to be timestamped close together (same session or adjacent days), so that the GitHub graph tells a story of real feature development.

11. As a CLI user, I want unrelated features to have visible gaps between them in the timeline, so that the graph doesn't look like a single uninterrupted coding binge.

12. As a CLI user, I want commit messages to follow conventional commit format with accurate descriptions of what each atomic commit does, so that the history is readable and professional.

13. As a CLI user, I want each commit to be ordered so that dependencies come first (types before implementations, configs before code), so that every commit in the sequence is self-consistent.

14. As a CLI user, I want the agent to detect when commit messages don't match the actual code changes, and automatically fix them via the Auditor backprop loop, so that I don't have to manually correct misleading messages.

15. As a CLI user, I want the agent to detect when unrelated hunks were merged into one commit group, and automatically split them back out via the Auditor backprop loop, so that atomicity is maintained without manual intervention.

16. As a CLI user, I want the agent to detect when related hunks were split across multiple commits, and automatically merge them via the Auditor backprop loop, so that logical units of work stay together.

17. As a CLI user, I want running `chronicle backfill` twice on the same diff with no changes to produce identical results without re-querying the LLM, so that I don't waste API calls or time.

18. As a CLI user, I want to be able to force re-generation from scratch even when a cached plan exists, so that I can get a fresh result when I want one.

19. As a CLI user who partially applied a plan and cancelled, I want the next run to detect the partial state and offer to resume from where I left off, so that I don't re-analyze from scratch.

20. As a CLI user, I want to configure which AI model the Orchestrator uses separately from which model the worker agents use, so that I can use a capable model for planning and a cheaper/faster model for simpler tasks.

21. As a CLI user, I want every configured provider in `~/.config/chronicle/config.json` to accept a `model` field per agent role, so that I can route Orchestrator to Claude and Executor to a local model.

22. As a CLI user with a local Ollama instance, I want to configure Chronicle to use any OpenAI-compatible local endpoint as a provider, so that I can run entirely offline.

23. As a CLI user with a very large diff (thousands of changed lines), I want the analysis to complete without exceeding the model's context window, by using hierarchical summarization that only fetches full content for relevant hunks on demand, so that I never get "prompt too long" errors.

24. As a CLI user with a small diff (<200 lines), I want the analysis to use full file context in a single pass, so that the agent has the best possible understanding of my changes.

25. As a CLI user, I want the Agent to create a backup branch before executing any commits, so that I can recover my original state if something goes wrong.

26. As a CLI user, I want the Executor to handle git hook failures gracefully by offering to retry with `--no-verify`, so that pre-commit hooks don't block the entire backfill.

27. As a CLI user, I want the Executor to verify each hunk is staged exactly once via the Hunk Ledger, so that no git conflict or double-stage error ever occurs during execution.

28. As a CLI user, I want the Executor to roll back failed commit attempts (unstage, revert ledger entries to PENDING), so that partial failures don't leave the repo in a broken state.

29. As a CLI user who configures a free-form intent like "fill every day with at least one commit," I want the agent to respect that instruction and produce dense, daily coverage, so that my contribution graph looks the way I want.

30. As a CLI user who configures a free-form intent like "create a story of feature-by-feature development with gaps between features," I want the agent to cluster commits into feature groups with natural gaps between them, so that the graph shows recognizable phases of work.

31. As a CLI user, I want the `--date-range` flag to accept both natural language ("last 30 days", "this quarter") and explicit ISO dates, so that I control the timeline without editing config.

32. As a CLI user, I want the interactive menu (running chronicle without arguments) to offer the same commands as the CLI flags, so that both entry points feel consistent.

## Implementation Decisions

### Module Structure

The rewrite lives in `apps/cli/src/` in the existing monorepo. The old code is replaced entirely — not refactored. The directory layout:

```
src/
  agents/
    orchestrator.ts        # Supervisor agent — dispatches, manages backprop loop
    file-analyzer.ts       # Worker — reads git state, extracts hunks, classifies files
    commit-planner.ts      # Worker — groups hunks into logical commit groups
    message-writer.ts      # Worker — generates conventional commit messages
    timestamp-distributor.ts  # Worker — assigns feature-aware timestamps
    auditor.ts             # Reviewer — inspects plan, returns structured signals
    executor.ts            # Worker — stages hunks, creates commits, handles failures
  lib/
    hunk-ledger.ts         # Hunk Ledger state management (read, write, verify)
    context-budget.ts      # Token budget calculation, detail level determination
    git.ts                 # Git operations (status, diff, stage, commit, branch)
    config.ts              # Config file management
    cache.ts               # Plan cache (read, write, invalidate)
    output.ts              # Terminal rendering (plan summary, commit list, contribution preview)
    errors.ts              # Typed error classes
    models.ts              # Provider/model definitions
    telemetry.ts           # Telemetry client
  commands/
    backfill.ts            # CLI entry point — reads flags, calls Orchestrator, renders output
    config.ts              # Config subcommands (init, model, provider, prompt)
    status.ts              # Status command
    router.ts              # tRPC router wiring
    helpers.ts             # Model selection UI
  types/
    index.ts               # All Zod schemas and TypeScript types
  index.ts                 # CLI entry point
```

The web app (`apps/web/`) and telemetry worker (`apps/telemetry/`) are unchanged.

### Seven Agents — Roles and Tool Definitions

#### 1. Orchestrator

The central supervisor. It does not call tools that touch the filesystem or git directly — it delegates all such work to workers. Its only tools are for dispatching and collection.

State machine:

```
IDLE → INTENT_READ (read config + free-form instruction)
     → STATE_CHECK (git status, diff, cache lookup)
     → DISPATCH_FILE_ANALYZER → COLLECT_FILE_SUMMARIES
     → DISPATCH_COMMIT_PLANNER → COLLECT_COMMIT_GROUPS
     → DISPATCH_MESSAGE_WRITER → COLLECT_MESSAGES
     → DISPATCH_TIMESTAMP_DISTRIBUTOR → COLLECT_TIMESTAMPS
     → ASSEMBLE_PLAN
     → DISPATCH_AUDITOR → COLLECT_SIGNALS
         ├── signals empty → PRESENT_TO_USER
         └── signals non-empty → MERGE_SIGNALS_BACK
               → re-dispatch affected groups only
               → COLLECT → re-assemble → DISPATCH_AUDITOR (loop)
     → USER_APPROVAL
         ├── approved → DISPATCH_EXECUTOR
         └── rejected/cancelled → IDLE
     → CACHE_PLAN → IDLE
```

Tools:

| Tool | Input | Output |
|---|---|---|
| `read_config_intent` | none | `{ freeFormInstruction: string, modelConfig: Record<AgentRole, { provider, model }> }` |
| `get_git_state` | none | `{ isRepo: boolean, branch: string, status: GitStatus, diffHash: string }` |
| `check_cache` | `{ diffHash, configHash }` | `{ hit: boolean, plan?: CommitPlan, executionState?: ExecutionState }` |
| `invalidate_cache` | none | `{ ok: boolean }` |
| `dispatch_file_analyzer` | `{ files: FileChange[], diffs: Map }` | `{ hunks: HunkDescriptor[], summaries: FileSummary[] }` |
| `dispatch_commit_planner` | `{ summaries, hunks, intent }` | `{ groups: CommitGroup[] }` |
| `dispatch_message_writer` | `{ groups }` | `{ messages: CommitMessage[] }` |
| `dispatch_timestamp_distributor` | `{ groups, messages, intent, dateRange }` | `{ timestamps: Date[] }` |
| `dispatch_auditor` | `{ plan }` | `{ signals: AuditSignal[] }` |
| `present_to_user` | `{ plan, format }` | `{ action: "approve" | "modify" | "cancel", modifications?: Modification[] }` |
| `cache_plan` | `{ plan, executionState }` | `{ ok: boolean }` |

#### 2. FileAnalyzer

Reads the actual filesystem and git. Classifies files as analyzable or assets, extracts hunks, returns summaries and full content on demand.

Tools:

| Tool | Input | Output |
|---|---|---|
| `get_all_diffs` | none | `{ files: FileChange[], diffs: Map<string, string>, untracked: Map<string, string> }` |
| `classify_files` | `{ files, diffs, untrackedBytes }` | `{ classifications: Map<string, "analyzable" | "asset"> }` |
| `extract_hunks` | `{ filePath, diff }` | `{ hunks: Hunk[], summary: HunkSummary }` |
| `get_hunk_detail` | `{ hunkIds: string[] }` | `{ hunks: HunkDetail[] }` |

Where:

```typescript
type Hunk = {
  id: string;            // SHA-256 of hunk content — stable across runs
  filePath: string;
  status: FileChange["status"];
  hunkIndex: number;
  newStart: number;
  newEnd: number;
  addedLines: number;
  removedLines: number;
  changeType: "addition" | "deletion" | "modification" | "mixed";
};

type HunkSummary = {
  id: string;
  filePath: string;
  hunkCount: number;
  addedTotal: number;
  removedTotal: number;
  semanticLabels: string[];  // e.g., ["validation", "error-handling", "types"]
  preview: string;           // First N lines of the hunk
};

type HunkDetail = {
  hunkId: string;
  fullContent: string;       // Complete hunk diff text
  surroundingContext: string; // N lines before and after for file-level understanding
};
```

#### 3. CommitPlanner

Takes file summaries, groups hunks into logical commit groups. Uses hierarchical context — sees summaries first, requests full details only for hunks it's actively reasoning about.

Tools:

| Tool | Input | Output |
|---|---|---|
| `group_hunks` | `{ summaries, intent }` | `{ groups: CommitGroup[] }` |
| `request_hunk_detail` | `{ hunkIds }` | `{ details: HunkDetail[] }`  |
| `set_dependencies` | `{ groups }` | `{ groups: CommitGroup[] }`  |

Where:

```typescript
type CommitGroup = {
  id: string;
  name: string;
  description: string;
  hunkIds: string[];
  filePaths: string[];
  category: "setup" | "feature" | "fix" | "refactor" | "docs" | "test" | "chore" | "style";
  order: number;
  dependencies: string[];  // IDs of groups that must come before this one
};
```

#### 4. MessageWriter

Takes finalized commit groups, generates conventional commit messages.

Tools:

| Tool | Input | Output |
|---|---|---|
| `generate_messages` | `{ groups, styleReference }` | `{ messages: CommitMessage[] }` |
| `get_style_reference` | `{ count }` | `{ recentMessages: string[] }` |

Where:

```typescript
type CommitMessage = {
  groupId: string;
  subject: string;   // e.g., "feat: add password validation"
  body?: string;     // Optional body paragraph
};
```

#### 5. TimestampDistributor

Takes commit groups and messages, produces timestamps that respect feature coherence and the user's free-form intent.

Tools:

| Tool | Input | Output |
|---|---|---|
| `assign_timestamps` | `{ groups, messages, intent, dateRange }` | `{ timestamps: TimestampAssignment[] }` |

Where:

```typescript
type TimestampAssignment = {
  groupId: string;
  date: Date;
  sessionId: string;  // Groups commits into coding sessions
};
```

#### 6. Auditor

Reviews the complete plan and returns structured signals per commit group. Does NOT rewrite anything — it flags problems and the Orchestrator dispatches re-generation.

Tools:

| Tool | Input | Output |
|---|---|---|
| `review_plan` | `{ plan }` | `{ signals: AuditSignal[] }` |
| `verify_hunk_coverage` | `{ plan, ledger }` | `{ unassigned: string[], overlaps: string[][] }` |

Where:

```typescript
type AuditSignal = {
  groupId: string;
  issue: string;
  severity: "error" | "warning";
  category: "grouping" | "message" | "timing" | "dependency" | "overlap" | "coverage";
  suggestedAction?: string;  // e.g., "split group into 2", "merge groups 3 and 4", "regenerate message"
};
```

Auditor checks:
- Incoherent grouping — unrelated hunks merged into one commit
- Broken atomicity — related hunks split across commits unnecessarily
- Wrong messages — commit message doesn't match the grouped hunks
- Unrealistic timing — implausible pacing (commits 1 minute apart across days)
- Dependency violations — group B depends on group A but B comes before A
- Hunk overlap — same hunk ID appears in multiple groups
- Missing coverage — hunks from the diff not assigned to any group
- Intent mismatch — plan doesn't respect the user's free-form instruction

#### 7. Executor

Takes the approved plan, stages hunks exactly once via the Hunk Ledger, creates backdated commits, handles failures.

Tools:

| Tool | Input | Output |
|---|---|---|
| `read_ledger` | none | `{ ledger: HunkLedger }` |
| `verify_hunks_pending` | `{ hunkIds }` | `{ ok: boolean, conflicts: string[] }` |
| `stage_hunks` | `{ hunkIds }` | `{ staged: boolean, patch: string }` |
| `stage_full_file` | `{ filePath }` | `{ staged: boolean }` |
| `create_commit` | `{ message, date, author, noVerify }` | `{ hash: string, ok: boolean }` |
| `mark_committed` | `{ hunkIds, commitId }` | `{ ok: boolean }` |
| `rollback_hunks` | `{ hunkIds }` | `{ ok: boolean }` |
| `create_backup_branch` | none | `{ branchName: string }` |
| `unstage_all` | none | `{ ok: boolean }` |

### Hunk Ledger Schema

File location: `.chronicle/hunk-ledger.json` (in the repo being backfilled — NOT tracked by git; must be added to `.gitignore` by the tool if it doesn't exist).

```json
{
  "gitDiffHash": "sha256-of-original-git-diff",
  "configHash": "sha256-of-active-config-slice",
  "hunks": {
    "abc123def456": {
      "id": "abc123def456",
      "file": "src/auth.ts",
      "hunkIndex": 0,
      "status": "pending" | "committed",
      "commitId": null | "commit-3"
    }
  },
  "newFiles": {
    "src/newfile.ts": {
      "path": "src/newfile.ts",
      "status": "pending" | "committed",
      "commitId": null | "commit-5"
    }
  },
  "commits": {
    "commit-1": { "message": "feat: add user auth", "hash": "a1b2c3d", "applied": true },
    "commit-2": { "message": "fix: handle null", "hash": null, "applied": false }
  },
  "ledgerVersion": 1
}
```

Hunk IDs are SHA-256 of the hunk diff content (the `@@` header + all changed lines). This means:
- Same content diff across runs = same hunk IDs
- Partial staging doesn't change IDs (unlike line-number-based indices)
- Cache keys can include ledger state for accurate cache matching

### Context Budget Model

```typescript
const OVERHEAD = 2800; // system + instructions + ledger state in tokens

function determineStrategy(
  totalChangedLines: number,
  modelEffectiveLimit: number,
): { detail: "full" | "compact" | "summary"; maxPasses: number } {
  const available = modelEffectiveLimit - OVERHEAD;
  const estimatedTokens = estimateTokensFromChangedLines(totalChangedLines);

  if (estimatedTokens <= available) return { detail: "full", maxPasses: 1 };
  if (estimatedTokens <= available * 2) return { detail: "compact", maxPasses: 2 };
  return { detail: "summary", maxPasses: 3 };
}

// Token estimation: ~5 tokens per changed line (conservative for code diffs)
function estimateTokensFromChangedLines(lines: number): number {
  return lines * 5;
}
```

Detail levels:

| Level | What FileAnalyzer returns | What CommitPlanner sees | Max hunks per pass |
|---|---|---|---|
| `full` | Complete hunks + file context | Everything | Unlimited |
| `compact` | Complete hunks, summarized file context | All hunks, trimmed context | 120 |
| `summary` | Hunk summaries only (labels, counts, previews) | Summaries; requests details via `get_hunk_detail` | 30 summary, then drill |

### Backprop Loop — Detailed Flow

The Auditor returns structured signals per commit group. The Orchestrator does NOT re-run the entire pipeline. It identifies which workers need to re-process which commit groups and dispatches targeted re-generation:

```
Auditor returns:
  [
    { groupId: "commit-3", severity: "error", category: "message",
      issue: "Message says 'add validation' but hunks are about error handling" },
    { groupId: "commit-3", severity: "error", category: "grouping",
      issue: "Contains hunks from both src/auth.ts and src/api.ts — unrelated" },
    { groupId: "commit-5", severity: "error", category: "timing",
      issue: "Timestamped 1 minute after commit-4 but commits are in different features" }
  ]

Orchestrator dispatches:
  → MessageWriter re-generates only commit-3's message
  → CommitPlanner re-processes only commit-3 and commit-4 (split)
  → TimestampDistributor re-processes only commit-5
  → Re-assemble plan
  → Dispatch Auditor again
  → Loop until clean or max iterations
```

Max iterations: configurable, default 3. After max iterations, present best-effort plan to user with Auditor's remaining signals as annotations.

### Error Handling Matrix

| Failure Point | Action | User Sees |
|---|---|---|
| Not a git repo | Stop immediately | "Not a git repository" |
| No changes found | Stop immediately | "No changes to backfill" |
| FileAnalyzer can't read file | Skip file, continue, report at end | Warning: "Could not read file X" |
| CommitPlanner returns empty groups | Stop with error | "Could not group changes" |
| MessageWriter fails for one group | Retry 2x, then use fallback "category: name" | Warning: "Using fallback message for group X" |
| TimestampDistributor fails | Use even distribution fallback | Warning: "Using even distribution" |
| Auditor loop exceeds max iterations | Present best-effort plan with annotations | "Auditor found remaining issues: ..." |
| User cancels approval | Stop, cache partial state | "Operation cancelled" |
| Executor: hunk already committed | Rollback, report to Orchestrator | Error: "Hunk X already committed — this is a bug" |
| Executor: git hook fails | Offer --no-verify retry | "Git hooks failed. Retry without hooks?" |
| Executor: commit fails (non-hook) | Rollback hunk, continue next commit | Warning: "Commit X failed: ..." |
| Executor: partial execution | Cache partial state, report summary | "5/7 commits created. Resume with --resume" |
| All providers unavailable | Stop with helpful message | "No working model available for role X" |

## Testing Decisions

### What Makes a Good Test

- Tests exercise **external behavior only** — the plan that comes out of Orchestrator, the commits that Executor produces, the ledger state after execution. Never the internal choices an LLM made.
- AI calls are **mocked at the transport level** — replace the actual model with a deterministic stub that returns known responses. Do NOT mock individual agent functions.
- Git operations are tested against **real temporary repos** created with `git init`. No mocking of git.
- The Hunk Ledger is tested as a **pure state machine** — given input state + operation, assert output state.
- The context budget model is tested as a **pure function** — given token estimates + model limit, assert strategy.

### Existing Prior Art

The current codebase has these test patterns that serve as prior art:

- `backfill-integration.test.ts` — Creates temp git repos with `mkdtempSync`, runs `$`git init``, writes files, runs git operations, asserts commit log output. This pattern is reused for all Executor tests.
- `ai.test.ts` — Mocks `globalThis.fetch` to block network calls, then tests behavior when AI is unavailable.
- `distribution.test.ts` — Pure function tests: pass in commits, assert stats and distribution properties.
- `ai.test.ts` via `__internal` — Exports internal pure functions for direct testing without any AI calls.

### Test Structure

```
tests/

  file-analyzer.test.ts     # Hunk extraction, classification, summaries

  message-writer.test.ts    # Message generation (pure, with mock groups)
  timestamp-distributor.test.ts  # Timestamp assignment (pure, with mock groups)

```

### Highest Seam: End-to-End Integration Test

The single highest-value seam tests the full Orchestrator flow:

```typescript
// Pseudocode for the end-to-end test
test("full pipeline produces expected commits", async () => {
  // 1. Create temp git repo with known changes
  const dir = mkdtempSync();
  await $`git init`.cwd(dir);
  writeFileSync(join(dir, "src/auth.ts"), "initial auth code");
  writeFileSync(join(dir, "src/api.ts"), "initial api code");
  await $`git add .`.cwd(dir);
  await $`git commit -m "initial"`.cwd(dir);

  // 2. Make specific, known changes
  writeFileSync(join(dir, "src/auth.ts"), "modified auth code\nwith validation");
  writeFileSync(join(dir, "src/api.ts"), "modified api code\nwith new route");

  // 3. Mock AI responses at the transport level
  // (mock returns predetermined hunk groups, messages, timestamps)

  // 4. Run Orchestrator with dryRun=false
  const result = await orchestrate(dir, { dryRun: false });

  // 5. Assert git history
  const log = await $`git log --oneline`.cwd(dir).text();
  expect(log.split("\n")).toHaveLength(3); // initial + 2 new commits

  // 6. Assert Hunk Ledger state
  const ledger = readHunkLedger(dir);
  expect(Object.values(ledger.hunks).every(h => h.status === "committed")).toBe(true);

  // 7. Assert no uncommitted changes remain
  const status = await $`git status --porcelain`.cwd(dir).text();
  expect(status.trim()).toBe("");
});
```

This one test exercises the entire system end-to-end except for the actual LLM. All lower-level tests are decomposition of concerns into testable units.

## Out of Scope

- The web app (`apps/web/`) and telemetry worker (`apps/telemetry/`) remain unchanged. No new web-based graph visualization.
- No new AI providers. Only the existing providers (OpenAI, Anthropic, Gemini, OpenRouter, Ollama, Cloudflare, OpenCode Zen, Groq) plus the generic OpenAI-compatible local endpoint.
- No authentication, no user accounts, no API server (telemetry worker is unchanged as a passive ingestion endpoint).
- No GitHub integration beyond what `git` provides — no API calls to GitHub, no PR creation, no issue linking.
- No UI framework migration — Clack prompts and picocolors terminal output remain.
- No Docker container or cloud deployment for the CLI. It runs on the user's machine.

## Further Notes

### Domain Glossary

| Term | Definition |
|---|---|
| **Backfill** | The act of taking uncommitted changes and creating a realistic commit history with backdated timestamps |
| **Hunk** | A contiguous block of changes within a file diff, delimited by `@@` lines in unified diff format |
| **Hunk Ledger** | A JSON state file tracking every hunk's lifecycle — from discovery to pending to committed |
| **Commit group** | A logical unit of work — a set of related hunks that form one atomic commit |
| **Feature coherence** | The property that commits belonging to the same feature are timestamped close together in the timeline |
| **Backprop loop** | The iterative process where Auditor flags issues, Orchestrator re-dispatches targeted workers, and the plan is refined — analogous to backpropagation in neural networks |
| **Context budget** | The token allocation strategy that determines how much diff content each agent call receives, degrading gracefully from full context to hierarchical drill-down |
| **Agent role** | One of the 7 agent positions (Orchestrator, FileAnalyzer, CommitPlanner, MessageWriter, TimestampDistributor, Auditor, Executor), each configurable with its own model |
| **Free-form intent** | A user-provided natural language string in config describing how the commit history should look |
